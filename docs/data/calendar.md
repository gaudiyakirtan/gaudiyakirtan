# Calendar (lunar month → songs)

**Spec version:** 2

> Conventions (uid, script codes, types) are in [`README.md`](README.md).

## Purpose

Answers "what should be sung today?" by locating a civil date in the Gaudiya lunar calendar
and returning the songs associated with that month, plus the daily ārati slots.

This is an **overlay**, not a new catalog entity: it holds no titles or lyrics, only
`song_uids` that resolve through the [Manifest](manifest.md) — the same referencing style
[SongGroup](collections.md) uses.

## Data source

`calendar.json` is generated by `pipeline/build_calendar.py` from three independent
inputs, merged in `pipeline/gaudiya_months.json`:

| Source | Supplies |
|--------|----------|
| `gaudiya_calendar.py` (Meeus ch.49/25 + Lahiri ayanāṁśa) | the lunar month windows |
| Śrī Caitanya-pañjikā (3866 events, 2011–2027) | which observances fall in which month |
| @madhudas livestreams (2172 dated, 2020–2026) | which songs are *observed* in which month |
| Śrī Gauḍīya Gīti-guccha, 7th ed. | stated rubrics (ārati slots, Ekādaśī) |

### Why the windows are precomputed

The Gaudiya month is an astronomical quantity. Implementing it separately in TypeScript,
Swift and Kotlin would give three floating-point ports that drift apart at month boundaries.
The pipeline computes it once and ships an explicit window table; each platform does a
date-range lookup only. This follows the locked ROADMAP decision — *static bundle,
offline-first, no runtime backend*.

## Shape

### `Calendar`

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `spec_version` | int | yes | This spec's version. |
| `generated` | date | yes | Build date. |
| `window_start` / `window_end` | date | yes | Coverage bounds of `windows`. |
| `windows` | list\<LunarWindow\> | yes | Contiguous half-open month spans. |
| `months` | list\<MonthBlock\> | yes | 12 lunar months + one `Adhika` block. |
| `daily` | list\<DailySlot\> | yes | Time-of-day ārati slots. |
| `festivals` | list\<Festival\> | yes | Dated observances, for "upcoming festivals" surfaces. |
| `basis_legend` | map\<string,string\> | yes | Meaning of each `basis` value. |

### `LunarWindow`

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `start` | date | yes | First day, **inclusive**. |
| `end` | date | yes | **Exclusive**; equals the next window's `start`. |
| `new_moon` | date | yes | New moon falling inside the window. |
| `lunar_month` | string | yes | Kārtika, Śrāvaṇa, … |
| `gaudiya_month` | string | yes | Dāmodara, Śrīdhara, … |
| `adhika` | boolean | yes | `true` for Puruṣottama (intercalary) months. |

### `MonthBlock`

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `lunar_month` | string | yes | Join key for `LunarWindow.lunar_month`. |
| `gaudiya_month` | string | yes | Viṣṇu-name of the month. |
| `observances` | list\<string\> | yes | Festivals falling in this month. |
| `note` | string | no | Editorial note. |
| `songs` | list\<SongRef\> | yes | May be empty (see invariants). |

### `Festival` *(spec v2)*

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `id` | string | yes | Stable slug, e.g. `sri-sri-radhastami`. |
| `name` | string | yes | Display name. |
| `months` | list\<string\> | yes | Gregorian months it falls in (may span two). |
| `dates` | list\<date\> | yes | Observance dates from the pañjikā, ascending. **Non-empty.** |
| `songs` | list\<SongRef\> | yes | May be empty — many observances have no song in the corpus. |

Dates come from the Śrī Caitanya-pañjikā and are **actual observance days**, unlike `windows`
which resolve months only. Note the pañjikā has a coverage gap (2025-04 → 2026-02) and no entries
past 2027-04; a festival with no future date simply stops appearing as "upcoming".

### `SongRef`

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `uid` | ref\<Song\> | yes | Resolves through the Manifest. |
| `basis` | enum | yes | `observed` \| `panjika` \| `book` \| `thematic` |

`basis` records *why* a song is attached, so UI can rank or filter by evidence strength:

- `observed` — month-concentrated across dated livestreams
- `panjika` — the pañjikā dates a matching observance in that month
- `book` — stated in the Gīti-guccha (section heading or rubric)
- `thematic` — subject matter fits; no dated evidence

## Invariants

- `windows` covers `[window_start, window_end)` with **no gaps and no overlaps**: every
  window's `end` equals the next window's `start`, so a date matches exactly one window.
- Every `LunarWindow.lunar_month` has a matching `MonthBlock`.
- Every `SongRef.uid` resolves to an existing [Song](song.md); the pipeline drops any that
  don't rather than shipping dead references.
- `months` contains exactly 13 blocks — 12 lunar months plus `Adhika`.
- A `MonthBlock.songs` **may be empty**. Pauṣa legitimately has no festival songs in the
  corpus; callers must render an empty state or fall back, never fabricate rows.

## Accuracy limits

- **Boundary days carry ±1 day uncertainty.** Whether a closing full-moon day belongs to the
  ending or beginning month depends on whether the full-moon instant precedes local sunrise,
  which needs a location this table does not model.
- **Use the pañjikā, not this table, for exact observance dates.** `windows` answers "which
  month is it"; it does not claim a festival falls on a specific day.
- `WINDOW_END` is 2036-01-01. Regenerate before then.

## Example

```jsonc
// windows[]
{ "start": "2026-10-26", "end": "2026-11-24", "new_moon": "2026-11-09",
  "lunar_month": "Kārtika", "gaudiya_month": "Dāmodara", "adhika": false }

// months[]
{ "lunar_month": "Kārtika", "gaudiya_month": "Dāmodara",
  "observances": ["Kārtika/Dāmodara-vrata (month-long)", "Govardhana-pūjā / Annakūṭa"],
  "songs": [{ "uid": "K1", "basis": "observed" }, { "uid": "D6", "basis": "panjika" }] }
```

## Platform notes

**All platforms.** The lookup is a date-range scan over `windows` — do not reimplement the lunar
arithmetic. If a platform ever computes a month boundary itself, the three apps will disagree at
boundaries; that is the specific failure this precomputed table exists to prevent.

Resolve dates in the device's **local** timezone. Converting to UTC first shifts the date by a day
for users west of Greenwich in the evening, silently returning the wrong month.

**Web.** The repository must stay client-safe (import the JSON as a module, not via `fs`). Today's
date is a runtime property of the *user's* device, so a build-time repository structurally cannot
answer it — unlike Manifest and Song, which are legitimately build-time.
See `web/src/services/calendarRepository.ts`.

**iOS.** Bundle `calendar.json` alongside the corpus; decode with `Codable`. `end` is exclusive —
use `..<`, not `...`.

**Android.** Ships in `assets/`; decode into a Room-independent value type (this overlay is derived
data, not user state, so it needs no persistence layer of its own).
