## Stage 4 — Madhukar das livestreams (@madhudas) — deriving the calendar the book lacks

Time probes in this stage are real (epoch `1784777036` ≈ 2026-07-22).

**Issue — homebrew `yt-dlp` broken** (`AttributeError: module 'certifi' has no attribute 'where'`,
from a shadowing venv at `~/.config/config-venv`).
- **Chosen:** use `~/workspace/.venv/bin/yt-dlp` instead.
- **Why:** it has a working certifi; no need to repair the system install.

**Issue — flat playlist listing has no dates.** 2,355 streams listed, but `--flat-playlist` returns
`upload_date = NULL` for all.
- **Alternatives:** (a) accept no dates; (b) fetch full metadata per-video serially (~2s each ≈ 78
  min); (c) parallelize.
- **Chosen:** (c) — split ids into 79 chunks of 30, run 10 workers via `xargs -P 10`, in the
  background.
- **Why:** ~8–20 min wall time vs. over an hour serial; dates are essential to the whole exercise.
  Result: **2,172 of 2,355 resolved**, spanning **2020-11-05 → 2026-07-22** (183 private/deleted/live).

**Issue — TSV delimiter bug.** `yt-dlp --print` emitted a *literal* backslash-`t`, not a tab, so the
first analyzer run crashed (`IndexError`). Fixed by splitting on `\\t`.
- **Why:** a silent parse failure that would have zeroed the dataset.

**Issue — title→manifest matching is hard (naming divergence).** The book/streams write Bengali ৱ as
`ŵ`; the pipeline's ISO 15919 writes it `y` (`tuŵā`→`tuyā`). Manifest stores full first-lines while
stream titles are prefixes; `śrī` is attached. Naive normalization matched 5/11.
- **Alternatives:** exact-only; substring; collapse the whole v/w/b/y/j consonant set + strip
  diacritics + prefix-match.
- **Chosen:** the consonant-collapse normalizer with exact→prefix→containment fallback (13/15;
  remaining misses were legitimate corpus duplicates like Dāmodarāṣṭakam K1/K23).
- **Why:** mirrors the pipeline's own `norm()` and matches the real orthographic variation.

**Decision — separate *seasonal* songs from *sequential curriculum*.** Computed a concentration
metric: share of a term's mentions in its densest circular 3-month window (25% = uniform).
- **Why:** most of the channel is daily sequential scripture study (Śrīmad-Bhāgavatam 479 mentions,
  32% concentration — flat/year-round), which would produce garbage seasonality if treated as
  rotation. **Dāmodarāṣṭakam scored 52 mentions, 100% Oct–Nov** — the decisive finding that the book
  omits. Curriculum series (Bhāgavatam, Caitanya-bhāgavata, the BGD Śaraṇāgati day-series) were
  explicitly flagged as *not* seasonal in the output.

**Decision — use the channel's own boundary markers as ground truth.** Rather than approximate lunar
dates, used stream titles literally marking "First Day of Kārtika" / "Final Day of Kārtika-vrata":
Kārtika 2024 = Oct 17→Nov 15, Kārtika 2025 = Oct 7→Nov 5.
- **Why:** empirical, exact, and later reused to validate the astronomy engine.

**Decision — tag every song→occasion link with provenance** (`observed` / `panjika` / `book` /
`thematic`) in `occasions.json` and `calendar_songs.json`.
- **Why:** never flatten an empirically-observed link into the same class as a thematic guess. This
  provenance model persisted into the shipped `calendar.json`.

**Issue — corpus gaps.** Several book-assigned occasion songs are not in the 703: the only explicit
Ekādaśī song (`Śrī Hari-vāsare…`), the sunrise Aruṇodaya kīrtanas, Madhyāhna Bhoga Ārati, Tulasī
Parikramā, Nṛsiṁha-stuti. Recorded rather than faked.

## Stage 6 — Śrī Caitanya-pañjikā Google Calendar (ICS)

**Decision — pull the public ICS feed, no auth.** `basic.ics` for the group calendar returned
HTTP 200, 1.38 MB, `X-WR-CALNAME: Śrī Caitanya-pañjikā for Vṛndāvana` — the authoritative Gaudiya
calendar, **3,866 events 2011-12-14 → 2027-04-20**.
- **Alternatives:** Google Calendar MCP (needs OAuth).
- **Chosen:** the `.../public/basic.ics` endpoint.
- **Why:** public calendars expose ICS with no credentials; fastest path and offline-parseable.

**Issue — two naming eras in the feed.** Early events are ASCII with `A:`/`D:` prefixes; later ones
use diacritics + 🅐/🅓 emoji, and Sanskrit `Avirbhava:`/`Tirobhava:` for appearance/disappearance.
Naive grouping gave 197 apparent festivals; unfolded → **140 canonical**.
- **Chosen:** a `canon()` that strips emoji/diacritics and folds spelling variants; classify
  `Avirbhava/Tirobhava` as appearance/disappearance.
- **Why:** the same festival must line up across years despite era-dependent spelling.

**Issue — day-of-year drift wraps at the Dec/Jan boundary** (festivals showed ±363d).
- **Chosen:** measure the *tightest circular* 3-month span instead of max−min.
- **Why:** solar events (Makara Saṅkrānti) then read ±1d and lunar ones ±19–27d — the real, usable
  signal.

**Issue — the pañjikā has a coverage hole (2025-04 → 2026-02) and no Pūrṇimā events after 2024.**
Discovered when trying to derive lunar boundaries from the calendar's own moon events.
- **Consequence:** could **not** use the calendar for month boundaries — forced the astronomy engine
  in Stage 8. Recorded as a caveat wherever "upcoming" is computed.

**Decision — merge three independent sources** (pañjikā dates + stream evidence + corpus uids) into
one map, each song link provenance-tagged. Moved the pañjikā data out of the temp scratchpad into
`song-pipeline/` so the build is reproducible.
- **Why:** filesystem-as-truth; a temp scratchpad is not a durable input.

## Stage 8 — Integrating the calendar into the mono web API

**Decision — precompute lunar windows in Python; ship a lookup table.** Rather than port Meeus'
astronomy to TS/Swift/Kotlin, `gaudiya_calendar.py` (Meeus ch.49 moon phases + ch.25 solar longitude
+ Lahiri ayanāṁśa, pure stdlib) computes once; `build_calendar.py` emits `calendar.json`.
- **Alternatives:** three per-platform floating-point ports.
- **Chosen:** precompute + ship an explicit window table; each platform does a date-range lookup.
- **Why:** three independent FP implementations *will* drift at month boundaries; and it matches the
  locked ROADMAP decision — static bundle, offline-first, no runtime backend.

**Decision — validate the engine against Stage 4 ground truth before trusting it.** All five Kārtika
window checks passed to the day; adhika-māsa cadence matched 2012/2015/2018/2020/2023/2026/2029.

**Issue — adhika-māsa logic was backwards.** First pass tested the *previous* new moon (labels the
second month of the pair as leap). Fixed to test the *next* new moon — the month whose own lunation
contains no saṅkrānti. This made 2026's leap month land May 16 → Jun 15, matching the stream's "Last
Day of Puruṣottama-vrata" (2026-06-15).
- **Why:** correctness, cross-checked against an independent observed date.

**Issue — validator caught 198 boundary collisions.** First `calendar.json` used *inclusive* ranges;
consecutive windows shared their boundary date. Root cause is real: a month's closing full-moon day
is also the next month's first day depending on local sunrise, which the table doesn't model.
- **Alternatives:** pick one side arbitrarily; model sunrise (needs a location).
- **Chosen:** **half-open intervals** (`start ≤ d < end`, `end === next.start`), with the ±1-day
  boundary uncertainty documented in the spec.
- **Why:** makes date lookup total and unambiguous; honest about what the table can't resolve.

**Decision — spec-first, matching the doc-driven workflow.** Wrote `docs/data/calendar.md` (spec v1)
before code; then `models/Calendar.ts`, `decodeCalendar()` at the existing decode boundary,
`calendarRepository.ts`, barrel export, and 20 tests against the real bundled JSON.

**Decision — the calendar repository must be client-safe.** Imports `calendar.json` as a module (not
via `fs`), like `songGroupRepository`, unlike `manifestRepository`.
- **Why:** "what should I sing today?" depends on the *user's* current date, which a build-time
  repository structurally cannot know.

**Decision — resolve dates in local time, never `toISOString()`.**
- **Why:** UTC conversion shifts the date by a day for users west of Greenwich in the evening (Bay
  Area, every evening).

**Verification:** 63/63 web tests, tsc clean, eslint clean, `calendar.json` (43 KB) written to all
three platform data dirs.

## Stage 13 — Tags, time, and location questions

**Decision — tags won't drive time recommendations, but have two real uses.** After the parallel
session's 212→21 group rework, the 14 topics are theological (Śrī Kṛṣṇa, Pañca-tattva…), not
temporal. Only `topic-arati` (7) and `topic-ekadasiparanaprasada` (7) carry weak time signal — both
weaker than `calendar.json`'s `daily[]`.
- **Chosen:** use tags as (a) a Pauṣa-style empty-month fallback and (b) within-month tie-breaking —
  not as a selection driver.

**Decision — reject IP geolocation; use device timezone + local sunrise.** The pañjikā is literally
"for Vṛndāvana" — pañjikās are per-city because tithi boundaries resolve at local sunrise. Fixed
clock windows are off by up to 2.6h (SF) to 6.2h (Stockholm) seasonally.
- **Alternatives:** IP geolocation ("where you're requesting from").
- **Chosen:** Tier 1 device-timezone → representative lat/long → local sunrise (Meeus, ~30 lines, no
  network); Tier 2 optional city picker; Tier 3 (GPS) skip.
- **Why:** there is no server to geolocate (static/offline); device tz is free, permission-less, and
  more reliable than IP; sending an IP off-device breaks the "no data collected" posture.

## Cross-cutting principles that recurred all session

- **Honesty over filler.** No fabricated popularity; no invented contact email; empty states
  (Pauṣa month, songless festival, no-address contact) say so plainly and never fabricate rows.
- **Provenance is never flattened.** `observed` / `panjika` / `book` / `thematic` tags survive from
  the stream analysis all the way into the shipped `calendar.json` and the UI ranking rule.
- **Precompute once, don't port maths.** The lunar engine runs in Python; platforms do table
  lookups — matching the locked static/offline-first architecture.
- **Local time, never UTC**, for anything date-dependent.
- **Spec-first (doc-driven loop).** Every feature got a `docs/…` spec (or a version bump) before or
  alongside code; the conformance matrix and ROADMAP were kept in sync.
- **Distinguish my failures from the parallel session's.** Throughout, a second session was editing
  the same tree (A0 removal, 24→7 book collapse, `VerseListItem`/`SongScreen` drift, pipeline
  vendoring `song-pipeline/` → `pipeline/`); each anomaly was attributed by mtime/scoping and reported
  faithfully rather than claimed as green.
- **Verified, not assumed.** Repeatedly corrected my own earlier claims once evidence appeared
  (corpus already bundled; A0 already gone; site repo *is* local; 404s were a stale server; adhika
  logic backwards; `/pronunciation` doesn't collide).
