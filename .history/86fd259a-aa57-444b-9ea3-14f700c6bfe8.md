- **Why:** the original urgency ("not version-controlled") was wrong; the real, still-valid point was that
  `song-pipeline` is a *separate* local-only repo. Revised the architecture advice accordingly.

## Stage 1 — Pipeline reorg ("add all of this in, make the new location work")

Scope requested: (1) move the pipeline into `mono`, (2) bundle covers into iOS/Android, (3) add a
`SOURCES.md`, (4) make everything work from the new location.

**Decision — vendor `song-pipeline` into `mono/pipeline/` by copy (not move/subtree).**

- **Chosen:** `rsync` copy (excluding `.git`, `__pycache__`, `.DS_Store`, `.gstack`, `.vscode`, `.claude`),
  leaving the original `song-pipeline/` untouched as a backup. 1,456 files / 35 MB; counts verified to match
  source (22 py, 705 converted, 706 songs).
- **Why:** `song-pipeline` was a separate local-only repo with no shared history/remote — subtree merge was
  complex for little value. Copy is simple and reversible; **did not delete the original** because deletion is
  the one irreversible step and wasn't explicitly authorized.

**Decision — rewrite hardcoded paths repo-relative.**
- 20 references to `../gaudiyakirtan-mono/...` across 6 scripts rewritten to `../...` (pipeline now sits *inside*
  mono, so `HERE/../web` == `mono/web`). Verified: all 10 target paths resolve, and both transliteration scripts
  dry-run cleanly from `pipeline/` (idempotent, already-applied results).
- **Why:** minimal, uniform substitution that preserves the "run from the pipeline dir" contract.

**Issue + Decision — covers do not work the way the request assumed.**

- **Chosen (now):** did **not** scatter dead-weight files into native. Canonicalized the 7 covers into
  `pipeline/assets/covers/` (byte-identical to web) and documented both routes in `SOURCES.md`, recommending
  **Route A (S3)**. **Why:** avoid a misleading half-wired state and an untestable blind native code change;
  surface the contradiction rather than proceed on the wrong assumption.

**Decision — create `pipeline/SOURCES.md`.**

## Stage 3 — Mirror blocker, then the coming-soon approach

**Issue — the mirror repo cannot be created from here.**
- `gaudiya-kirtan` is a **User** account (node id `U_…`), not an org; the authed CLI user `kendreaditya` cannot
  create repos inside another user's namespace. Additionally, `gaudiya-kirtan/gaudiyakirtan` currently
  **redirects to `gaudiya-kirtan/coming-soon`** (coming-soon was renamed from `gaudiyakirtan`), so that name is
  effectively taken.
- **Decision:** recommended **skipping the mirror** and deploying `gaudiyakirtan/gaudiyakirtan` directly (Vercel
  can connect the org repo). **Why:** removes the blocker, no second repo, no PAT/sync machinery.

**Decision — user's counter-proposal: reuse the `coming-soon` repo via a branch.**
- Verified: `kendreaditya` has `push: true` on `gaudiya-kirtan/coming-soon`, which is a **root-level Next.js
  App-Router** project already wired to Vercel + Cloudflare.
- **Chosen structure:** put the web app at the **branch root** (not full monorepo with root=`web`).
  - **Alternatives:** full mono on the branch with Vercel Root Directory = `web` (requires changing the shared
    coming-soon project's root, which would break its `main`/production deploy); web-at-root.
  - **Why web-at-root:** matches coming-soon's root-level layout so the existing Vercel project (or a new one)
    can branch-deploy it with domain-to-branch mapping and no root-dir conflict.
- **Executed:** confirmed `web/` is standalone (own `pnpm-lock.yaml`, zero `workspace:` deps). Built the `dev`
  branch from **git-tracked files only** via `git archive HEAD:web | tar -x` (814 files, no `node_modules`/`.next`).
  Pushed `dev` (`b261cf0`); verified `main`/live apex untouched and the local production build passes.

## Stage 4 — Direct Vercel deploy from the org repo, and the failure chain

User imported `gaudiyakirtan/gaudiyakirtan` (branch `mono`, Root Directory `web`) as a new Vercel Hobby project
`gaudiyakirtan-dev`.

**Issue #1 (~first deploy) — deploy failed at "Assigning Custom Domains" despite a clean build.**
- Initial hypothesis: a domain already owned by the `coming-soon` project (apex/`www`) was attached to the new
  project (Vercel forbids the same domain on two projects). Fix guidance: attach only `dev.gaudiyakirtan.com`.
- This turned out to be a red herring once the real gate error surfaced (below).

**Issue #2 — Vercel security gate: "Vulnerable version of Next.js detected."**
- Root cause found via `pnpm audit`: `next@15.2.4` carries **GHSA-9qr9-h5gf-34mp** (critical RCE in the React
  flight protocol, patched `>=15.2.6`), which Vercel **hard-blocks** at deploy. Several high DoS advisories also
  present, fully cleared only at `>=15.5.16`.
- **Alternatives:** `15.2.9` (clears only the critical), `16.2.11` (`latest`, major bump with breaking changes),
  `15.5.21` (`backport` tag = latest maintained 15.x).
- **Chosen: `next` + `eslint-config-next` → `15.5.21`.** **Why:** clears the critical *and* the high DoS
  advisories while staying on the same major to avoid Next 16 breaking changes. Rebuilt locally (736/736 pages),
  re-audited (critical gone; only transitive `sharp`/`postcss` highs remain — not what Vercel blocks on).
  Committed `42e72da`, pushed to `mono`.

**Issue #3 — `dev.gaudiyakirtan.com` served raw Markdown (`public/index.md`) at `/`.**
- Diagnosed by curl: both the Cloudflare-fronted domain **and** the direct `*.vercel.app` returned
  `content-type: text/markdown` at `/`, while `/songs`, `/about`, `/books`, `/songs/A1` all **404'd** and only
  static `public/*.md` files resolved. So Cloudflare was innocent — **Vercel was serving the `public/` folder as
  a plain static site and ignoring the Next.js build output** (`/` fell back to `public/index.md`).
- Confirmed with local `next start`: `/` correctly serves the HTML app there → **not a code bug**; the Vercel
  project's **Framework Preset wasn't Next.js**.
- **Alternatives:** change the dashboard Framework Preset (not deterministic / not in code); force it via
  `vercel.json`.
- **Chosen:** added `web/vercel.json` with `"framework": "nextjs"` + `"buildCommand": "pnpm run build"`
  (so the `prebuild` markdown-twin generation still runs). **Why:** deterministic, in-code, survives redeploys.
  Committed `30a8bf0`, pushed. *(User later added `"outputDirectory": null` to this file.)*
- **Observation:** a background poll showed the live site still Markdown/404 after ~5 min; the `/songs` 404
  content-type flipped `text/html` → `text/plain`, hinting a redeploy ran but still in static mode. Working
  hypothesis at the time: a dashboard **Output Directory** override outranking `vercel.json`.

**Issue #4 (current / open) — `ENOENT: no such file or directory, mkdir '/vercel/output/static/assets'`.**
- The build log for `30a8bf0` proved the framework fix **worked** (built as Next.js, 736 pages, reached
  "Collected static files (public/, static/, .next/static)"), then failed at the final static-collection step.
- Root cause found: `web/public/assets` is a **git symlink (mode 120000) → `../../assets`** (the mono-root
  `assets/` dir, 3.5 MB / 17 real files: logos + `months/` calendar images). Vercel's static collector can't
  reproduce a symlinked directory inside `public/`, so `mkdir …/static/assets` fails. It's the only symlink
  tracked under `web/`.
- **Alternatives:** (A) materialize — replace the symlink with the real 17 files inside `web/public/assets`
  (self-contained web, ~3.5 MB duplicated in-repo); (B) reverse the symlink (make `web/public/assets` the real
  home and symlink the mono root to it); (C) configure Vercel/Next to handle the symlink.
- **Chosen (planned): (A) materialize.** **Why:** simplest and most robust for a static `public/` asset with
  Root Directory = `web`; the web app needs the files bundled anyway; low risk to any other consumer of the
  mono-root `assets/`. **Status: not yet executed** — the session ended just after enumerating the 17 asset
  files to copy; the fix (remove symlink, copy real files, commit, push) remains the immediate next step.
